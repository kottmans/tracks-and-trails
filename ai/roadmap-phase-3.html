What to do next, in order

One ordering, and the reason for it. The numbers are a sequence rather than a ranking: each item unblocks or de-risks the one under it. Rewritten 2026-08-07 — the review queue emptied, so for the first time this phase every slot holds a deliverable rather than a correction.

  1. T-182 Rule on the excluded option families Maintainer, not implementer

    First because it is cheap to take now and expensive to meet by accident later, and because it is the only item here that nobody else can do. Six families point opposite a written constraint, and an implementer who meets one mid-task will resolve it in a commit rather than a decision. It blocks no Phase 3 work at all — which is exactly why it can be taken while the code work runs.

  2. T-181 The queue is stopped until Start Small, and user-facing

    Promoted above the format table deliberately. It is the smallest deliverable in the phase — the gate exists and already parks correctly — and it changes the first thing every user does, so it wants to be in the window early rather than landing on top of four other unfamiliar surfaces. It also fixes a live defect in passing: a relaunch currently resumes downloading with no user action.

  3. T-107 The format table Foundation

    Named High because REQ-008 and T-109 both act on this table. It also owns proving the phase's first exit criterion — the table matching yt-dlp -F for a fixture set — so it carries a gate as well as a feature. It is the head of the phase's only chain, and nothing else can shorten that chain.

  4. T-113 Resume across a restart Start early

    Startable today and deliberately not last: it reopens two accepted decisions and carries the phase's highest uncertainty. Discovering what it costs late is how a phase overruns — and it needs no spec, so nothing is lost by learning early. UX-006 did not touch it: the start gate moved a queue-level default, and P-10's per-job pause still arrives here.

  5. T-108 Video plus audio, merged After T-107

    Reads the table T-107 builds, and settles the ffmpeg-presence rule that T-109 then shares. Two exit criteria run through here: the merge itself, on both platforms.

  6. T-110 Playlists, properly Structural

    Changes what a job is, so it reaches core/ rather than the UI. Worth taking while the queue is freshly reviewed — T-137 and T-140 each moved part of the playlist story. (T-145 moved History's part of it, and that surface is gone.)

  7. T-109 Post-processing, seven options Largest

    The biggest item in the phase, and the one with a documented history of failing quietly: T-077 found four of five Phase 1 options never produced a file. Late in the order because it wants T-108's ffmpeg rule settled first.

T-111, T-112 and T-114 are not in this list because nothing about their order is contentious: T-111 follows T-109, T-112 follows the spec, and T-114 can be taken by anyone at any point. T-180, T-176 and T-143 are cleanup and belong in the gaps between the items above — T-180 carries the open T179-R3 and is a decision before it is a change.

The one thing on this board that is genuinely unscheduled is the size of Phase 4.5. T-183 is the task that turns yt-dlp's option list into tasks, and until it lands no estimate of that phase exists — not a rough one, not a range. What is known is the shape: eleven options are expressible today, Phase 3 and 4 add perhaps fifteen, and the option list runs to roughly 250 across sixteen groups, of which a real fraction is the command line itself rather than a capability. Quoting a size before the audit would be inventing one.

The other two came with the History removal, on maintainer direction

Its reasoning against dropping columns has now been superseded too — it refused a column drop because SQLite rewrites the table to keep every row, and migration 0009 keeps nothing.
  • ARCHITECTURE.md §10 gained an exception, and it is the judgement on this board most worth challenging. §10 forbade a destructive migration without a pre-migration backup. A backup here would leave the purged URLs in a second file beside the database — unreachable, unmanaged, removed by nothing — so the rule that protects data from a change which did not intend to touch it is inverted by one that does. The purge was the maintainer's ruling; reading it as also waiving the backup is a Planner judgement and is flagged as one in the document.

The review found exactly that, and it was right. T169-R1: satisfying a decision's trigger makes it eligible for a ruling, not self-ratifying — the same distinction as T145-R1 and T144-R1, which this project has now recorded three times. Four further findings followed, and the maintainer's ruling was to remove the feature rather than repair it. Five findings, two High, and not one about the warning being wrong: every one was about keeping the data.

The seventh is UX-001, amended 2026-08-07 — and the amendment is a default, not a semantic

  • UX-006: the queue runs only once started, and is stopped at every launch. Adding a URL enqueues it and starts nothing; the row reads Held, the word UX-005 already gave a waiting row. Stop drains exactly as UX-001 specified — in-flight sessions finish, nothing new starts, no partial file is created, and no job ever enters PAUSED.
  • It needed no new mechanism, which is the whole reason it is cheap. T-080 built the queue-level gate and T080-R1 already made it park a download while admitting a probe — so a stopped queue still resolves a paste, which is what makes reviewing a batch possible at all. What changed is which side of that gate the window opens on.
  • Acceptance criterion 1 gained a Start press, because without it the MVP criterion is satisfied by a build that downloads nothing.

It also fixes something nobody had filed. Restoring a queue currently resumes work with no user action — including after a crash, and including when the reason for relaunching was to remove something. And it deliberately does not answer P-10. Per-job pause is untouched and still arrives with T-113, on resume's terms, when a partial file finally has a defined meaning.

The target is capability parity, not flag parity, and the difference is load-bearing. A large share of yt-dlp's surface is the command line — --simulate, --print, --dump-json, --batch-file, the progress and quiet flags, config locations, aliases. This application is the caller of those and already sets several for the worker to function; exposing them would be exposing its own plumbing. So REQ-030 promises that no download reachable from the command line is unreachable from the GUI, and names the exclusions rather than quietly leaving them out. T-183's application-owned list is derived from build_options with a test asserting the two agree, so the refusal list cannot drift from what the code actually sets.

The risk this phase accepts, stated where it can be checked later: the escape hatch becomes the interface. A text field that takes command-line syntax makes every capability reachable and none discoverable, and it would be an easy phase to declare finished with the common options still being typed as flags. ARC-010 accepted that trade knowingly and the mitigation is an exit criterion rather than an intention — promotion of the options users actually type is deliverable work, and the phase does not exit while the common ones are still free text.

Distribution is not renumbered, and that is a choice rather than an oversight. "Phase 5" names the distribution phase in five documents and in every review record that cites it. Renumbering would rewrite the meaning of references nobody can retroactively correct, to buy an integer; 4.5 is uglier and cannot mislead.
