### Criterion 3 answers *both* ways, deliberately

The criterion says "refused **or** disambiguated, stated either way", and this implementation does
both, split on **who proposed the name**:

- **A name the user typed is refused** (`ValueError`) — `add_preset` and `update_preset`, built-ins
  included in the taken set. The caller is an editor with the user in front of it and can ask
  again; picking for them is how *Audio only (MP3) (2)* appears in a list nobody meant to create.
- **A name nobody proposed is disambiguated** — duplication proposes no name, so there is nothing
  to refuse. `free_preset_name` yields `X (copy)`, `X (copy 2)`, … and the proposal lands in the
  form where it is edited before it is saved.

That is a reading of the criterion, not a transcription of it. **If you think "stated either way"
means one rule for both paths, this is the finding to open.**

### Criterion 6 is met, but mostly *not by this diff*

Worth saying plainly rather than letting the table imply otherwise. `load`'s `ARC-008` table and
`_presets_from`'s per-entry drop-and-report came from **`1381f7f`, `T-109`'s corrections** — code
you have already reviewed. It is outside `c5997fd..bf30d82`.

What **is** new here is `ARC-008` reporting for the `default_preset` key this task introduced:
`_default_preset_from` reports a default naming nothing rather than silently correcting it
(`test_a_default_naming_nothing_is_reported_and_falls_back`,
`test_a_default_that_is_not_a_name_is_reported`), and omission stays silent because `save()`
promises it will (`test_a_file_that_omits_the_default_reports_nothing`).

So: the criterion holds across the codebase, and reviewing *this* diff alone will not show you all
of it. Read `core/settings.py` whole if you want to confirm the criterion rather than the change.

## What to look at hardest

- **`requires_ffmpeg` asks the question with a placeholder URL.** A preset carries neither URL nor
  output directory and `DownloadRequest` refuses both empty, so the request is built against
  `https://example.invalid/preset` — RFC 2606's reserved name, the stand-in `_freeze_probe` already
  uses. That is only honest because the answer does not depend on it, which
  `test_the_answer_does_not_depend_on_the_placeholder` asserts **across every built-in** rather than
  once. The alternative — a predicate reading the preset's own fields — was rejected deliberately:
  it is the hardcoded list `adapter.requires_ffmpeg`'s docstring records as having already missed
  processors once, and it would pass every test written today. One answer derived from yt-dlp's
  class hierarchy was preferred to two that can drift. **Check the placeholder is genuinely inert**
  — `test_requires_ffmpeg_touches_no_network_and_starts_no_worker` is the assertion, and it is the
  one I would most like a second pair of eyes on.
- **`Delete` on a built-in does nothing and is not drawn disabled.** `docs/UX_SPEC.md` §8's clause,
  implemented literally, silence included
  (`test_delete_on_a_built_in_does_nothing_and_writes_nothing`,
  `test_the_delete_button_is_not_drawn_disabled_for_a_built_in`). It is marked `[D]` — derived, not
  ruled — and a button that visibly does nothing is what `T-139` argues against elsewhere. **Worth
  a second look at whether the mark alone is enough**, or whether this needs a `[T]` and a ruling.
- **`default_preset_of` is total, and everything depends on that.** `P-7` is only true if it cannot
  answer nothing: a stored name that resolves to no preset, a deleted default, an empty string and
  a fresh install all have to land on a real preset. It falls back to the registry's first. The
  totality is load-bearing for `add_dialog`'s inheritance — if it can return `None`, a paste opens
  on nothing.
- **`_taken_names` imports `core.presets` inside the function** to avoid an import cycle between the
  settings layer and the registry it stores around. Pre-existing shape from `add_preset`, now shared
  by four more callers. Confirm the cycle is real and the local import is the right answer.
- **Standing risk focus (`REVIEWS.md`):** preset names reach TOML, so `_toml_string` /
  `_toml_character` are the filesystem-adjacent surface here —
  `test_a_name_carrying_a_control_character_does_not_destroy_the_file` and
  `test_every_control_character_survives_the_round_trip` cover the round trip, and
  `test_a_failed_write_leaves_the_previous_file_intact` covers the write.
