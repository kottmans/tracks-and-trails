## `T-128` — the segfault is diagnosed, and it was the harness

### What the evidence says

Both soak cores were still on the machine (`systemd-coredump`). `gdb` gives what a stack could
not: the faulting instruction is `receiver->d_ptr->threadData`, and the receiver's memory was
already recycled — vtable slot `0x00005567c4c40522`, not 8-aligned; `d_ptr` slot noise. **A
use-after-free**, which is why both runs died at the same test count rather than at random.

**The failing test is named from the traceback, not inferred.** The Python stack points at a
*fixture teardown*, which runs after pytest prints the progress character — so 97 dots means test
**#97**, `test_a_ready_job_starts_a_download_at_running`, not #98 as the task had computed. It is
the one test in that file running `child_downloading_forever`, so its teardown has a live worker, a
live `ResultPump` and a live log thread: the exact thread set both logs show.

**The precondition, reproduced deterministically.** `is_idle` answers a question about *work*; it
says nothing about the manager's own poll timer, which `_tick` stops on a later tick. Replaying
#97's teardown verbatim: `is_idle: True, timer active: True`. **Five teardowns** had that shape.

### Product or harness — harness, and the argument is checkable

- Nothing in `src/` reads `is_idle`. `app.py:556` connects to the `idle` **signal**, emitted only
  after `_timer.stop()`.
- The application holds one manager for the life of the process and never drops one.
- `is_idle` is **not changed**: it is correct about work, the product depends on the signal, and
  altering a public property to suit a fixture is the wrong direction.

### What is deliberately left unresolved

Two mechanisms produce this signature from the same precondition — cross-thread destruction (Qt
warns) and destruction *during* `activateTimers()` by the cycle collector (silent). Three full
runs with capture disabled produced **zero** cross-thread warnings, so the second is likelier.
**Recorded as unresolved rather than guessed**: the correction does not depend on which, because
both begin with a live timer on an object about to become garbage.

### Evidence

| Check | Result |
|---|---|
| Mechanism reproduction | **3/3, sub-second**, `gdb` signature byte-identical to the soak cores |
| Precondition, before | `is_idle=True, timer active=True` — deterministic |
| Precondition, after `drain` | `timer active=False` |
| Full suite | see the gate at the end |

### What a reviewer should attack

1. **`drain` asserts rather than falling through** its deadline — the `T122-R2` lesson applied to
   a new helper. Check it cannot pass a manager that never settled.
2. **`is_still_polling` uses `findChildren(QTimer)`**, public Qt API, rather than reaching for
   `_timer`. Check that is genuinely equivalent for every surface using it.
3. **The detector has never fired.** It guards the mechanism *not* evidenced here. Reasonable, or
   dead weight? I think it earns its place because the alternative signal is a segfault several
   tests later — but that is a judgement worth a second opinion.
4. **The soak has not been run.** The 60-run gate `OPS-007` now requires is unstarted. Nothing in
   this diff claims it has.

## `T-129` — the style sheet took the native style's metrics and states away

Found by opening the application. One cause, two symptoms: styling a widget class switches it to
`QStyleSheetStyle`, so anything the platform style supplied must come from the sheet or not at all.
`T-120` supplied colours — the two things that are *not* colours went missing.

| Symptom | Measured before | After |
|---|---|---|
| Group-box title over its own contents | title bottom **15 px below** contents top | **6 px clearance** (Qt's own style: 5) |
| Button hover fill | identical to idle (`surface`) | `sunken` |
| Selected menu item | identical to the rest | brand `primary` |

### The first version of the test passed for the wrong reason — recorded, not hidden

The hover tests first drew through `QApplication.style().drawControl(...)` **with no widget**,
which never consults the sheet. They compared two renderings, found them different, and passed —
measuring the *platform* style's hover, which was never at fault. **Both mutations survived.**
Corrected to draw through the widget and to assert **a colour the theme names** rather than "the
two differ". This is `ai/TESTING.md` §13 and it is written into the test file's own docstring.

### What a reviewer should attack

1. **`margin-top: 0.9em` is a magic number.** It is enough for the title at the default font; is
   it enough at 18 pt? `T118-R15` is the precedent for that question being worth asking.
2. **The assertion is "clearance exists", not a pixel count.** Deliberate — Qt's exact number is a
   platform detail — but it would pass a 1 px clearance that still looked wrong.
3. **`QListView, QTreeView, QTableView { selection-background-color }`** now sets selection colours
   application-wide. Check that does not fight `RowDelegate`'s own selected-state painting.
4. **Only the light theme is asserted.** The dark theme has still never been on a screen.

## `T-131` — the launch test used the developer's real database and instance lock

**Found by the gate for `T-129`, and it is not `T-129`.** Two launch tests failed. The cause was
neither the change under test nor the machine: `run_headless` redirected `XDG_CONFIG_HOME` only,
while the application uses three roots — config for `settings.toml` and `window.toml`, **data for
the queue database** and the yt-dlp copy, and cache for the log and thumbnails.

So every launch test opened the real `library.sqlite3` and took the real single-instance lock
(`T-087`). With the application running — which it was, because the maintainer had just started it
— the lock is held and the launch never completes. The test fails at its own 120 s timeout with no
window shown, which reads like an infrastructure hang.

| | Result |
|---|---|
| Application running, before | 2 tests fail, 120 s each |
| Application running, after | **4 passed in 0.71 s** |

The Windows overrides were already the complete pair. The POSIX side was one of three — so the
platform that had once been wrong ended up better covered than the one that always looked right.

**What a reviewer should attack:** the out-of-scope note. I did **not** audit the rest of the suite
for the same gap, and I think that should be deliberate work rather than something found by
whoever next has the application open.
