## §1 · `T193-R1` — the header was never counted

`EntryTable.sizeHint` asked `header.isVisible()`. **A widget is not visible until every ancestor is
shown**, and this hint is taken before the picker is mounted — so the header contributed `0`, the
hint was short by exactly its height, and every picker at or below the cap kept a scroll range.

**Now `header.isHidden()`**, which reports what was *configured* rather than what is on screen: it
is `False` for a header nobody hid, mounted or not, and `True` only when one is hidden deliberately.
`_build` hides the **vertical** header that way; the horizontal one is never hidden, which is why
its height must always count.

**One change beyond the finding, and you should judge whether it was warranted.** I also moved from
`header.height()` to `header.sizeHint().height()`. An unlaid-out widget's `height()` is a default
that has not met the font or the style — the same class of untrustworthy pre-mount answer as
`isVisible()`, and fixing one while leaving the other seemed like fixing the instance.

**Tests, per your correction direction:**

- **A mounted picker at 2, 6 and 8 entries has a scroll range of `0`** — parametrised, so the cap
  and the cases below it are one statement.
- **Above the cap it scrolls.** Without this the first test would pass on a picker so tall it never
  scrolls at any size, and the cap would be bounding nothing.
- Both drive `verticalScrollBar().maximum()` on a **shown** table, not arithmetic.

**Mutation:** `isHidden()` → `isVisible()` fails all three at-or-below-cap cases. Bytecode cache
cleared, `PYTHONDONTWRITEBYTECODE=1`.

## §2 · `T194-R1` — two handlers on one signal, and the last writer won

`_restore_current_row` uses `NoUpdate` deliberately. `_reopen_editor` — connected to the **same**
`modelReset` — then called `QListView.setCurrentIndex`, which selects. So the fix held for an
ordinary reorder and was undone whenever an editor happened to be open, which is why `T-194`'s own
tests agreed with it: **neither opened an editor.**

**Now through the selection model with `NoUpdate`**, unconditionally. Selection is
`_restore_current_row`'s to decide; this method only says where the editor goes.

**Two regressions, both directions as you asked:**

- **Unselected stays unselected** — the reported defect.
- **Selected stays selected** — so the fix cannot be "never select", which would satisfy the first
  test and be equally wrong.

Both open the editor through `QListView.edit`, which reaches the delegate's `createEditor` and sets
the `editing_job_id` that `_remember_editor` reads. **Setting `_reopen_for` directly would skip the
wiring under test.**

**Mutation:** restoring `self._list.setCurrentIndex(index)` fails the unselected regression. The
selected one passes under mutation, correctly — `ClearAndSelect` also leaves it selected, and that
test exists to catch the opposite over-correction.
