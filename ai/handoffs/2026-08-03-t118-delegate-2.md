## What the second round was really about

One mistake with three faces, and it is worth naming before the fixes: **I optimised away the thing
`UX-004` chose, and then wrote tests that agreed with me.**

`UX-004` §1 says every row carries a visible *Download as* control. Its `T-119` sequencing note
permits the delegate to draw it "only on the row under the pointer or holding focus: one widget
reused, **identical interaction**". I took the widget-reuse half and dropped the drawing. Then the
structural test I was most pleased with — the one that killed the widget-per-row mutation —

## The corrections

**`T118-R12`.** `RowDelegate._paint_control` draws the control on every row that has choices, using
`QStyleOptionComboBox` and `CC_ComboBox` through the widget's own style — the platform's combo box
rather than a rectangle that resembles one on this machine — carrying that row's current value, or
`INHERITED_TEXT` when it follows the batch. The live `QComboBox` still exists only for the row being
edited, so `R10`'s cost does not return. `editorEvent` opens that editor on a direct left-click
inside the control's rectangle; `SelectedClicked` alone meant the first click selected the row and
did nothing visible. One `_control_rect` serves the painted affordance, the editor geometry and the
click target, so the control cannot move under the pointer.

**`T118-R8`.** The drawn line is no longer narrowed by the control's slot and no longer elided — it
wraps into `SELECTOR_LINES` at the full body width. Because a delegate paints pixels rather than
selectable text, the copyable half is `selectorValue` below the list, which now follows the current
row and falls back to the batch when none is current. That is the "dedicated selectable detail" your
recommendation preferred over a tooltip.

**`T118-R13`.** `sweep()` resolves the names to keep and hands the listing, the stats and the
unlinks to `_SweepTask` on the pool. `close()` marks the store closed, cancels network work and
returns; the `waitForDone(5000)` is gone and ownership completes at `closed` when the last counted
task drains. What the wait protected is still handled — `QThreadPool`'s destructor waits for its
runnables, and that runs when the store is destroyed rather than on the interaction.

**Both regressions are deterministic, not timed.** They fill the pool with blockers, so "the call
returned without doing the work" is a fact about scheduling rather than a stopwatch reading: the
doomed file is still on disk when `sweep()` returns, and `closed` has not been emitted while a task
is outstanding. The `close()` mutation takes 5.11 s to fail, which is the wait it asserts the
absence of.

## What I got wrong this round

**The first version of the `R12` test was vacuous, and a mutation caught it.** It rendered the
control's slot and asserted it was "not blank" — which the item view's own background satisfies
whether or not a control is drawn. Disabling `_paint_control` passed it. That is the same shape as
the finding I was fixing, produced while fixing it. Rewritten to hold two rows identical apart from
`PRESET_CHOICES_ROLE`, both with empty text, so the only thing that can differ in the compared
rectangle is the control.

**The first `close()` regression asserted against foreign pool work.** My blockers bypass the
store's own counter, so `closed` fired legitimately and the test failed for a reason other than the
one it named. It now queues a real store task behind the blockers.

**A defect found by a flaking test, and deliberately left uncovered.** The cache write used
`write_bytes`, which creates the file and then fills it — so a reader could open a name that exists
and get a truncated image. Written aside and renamed now. **No test covers it**: the window is
unobservable to a deterministic test, and one that appeared to cover it would be worth less than
this paragraph. It surfaced only because a test raced its own write.
