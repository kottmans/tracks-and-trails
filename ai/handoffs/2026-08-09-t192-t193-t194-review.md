## §1 · `T-192` — the stopped-queue message hid at the right

**Symptom, from the maintainer:** the queue-gate message sat at the far right of the status bar,
against the environment summary, where it read as part of the summary rather than as something to
act on.

**What changed:** `statusBar().addWidget(...)` instead of `addPermanentWidget(...)` — Qt's
right-hand region — plus an `actionableStatus` dynamic property and a `QStatusBar QLabel[...]` rule
in `ui/theme.py` giving the stopped state `theme.warn` and `font-weight: 600`.

**The part worth attacking:** the emphasis is styled **by role, not by object name**, because
`test_the_sheet_styles_by_class_so_a_new_widget_inherits_it` requires it. The property is set and
the widget re-polished with `unpolish()`/`polish()` — **a property set without a repolish silently
does nothing**, which is the failure mode a passing test would not show if it asserted the property
rather than the rendered result.

**Second channel, deliberately:** `NFR-005` forbids information by colour alone, so the state is
legible in words, with weight and colour as reinforcement. `T-202` will sweep this properly; this
task should not have created a new instance.

## §2 · `T-194` — reordering a row scrolled the queue to the top

**Symptom:** using ↑/↓ to move a track resets the view to the top of the queue, so moving something
several places means scrolling back each time.

**What changed:** `ui/queue_view.py` remembers the current row on `modelAboutToBeReset` and restores
it on `modelReset`, **by job id**, with `scrollTo(index, EnsureVisible)`.

**Three things to check:**

- **By id, not by row number.** `T118-R14` established that reconciling A/B to B/A leaves row 0
  valid and meaning a different job. Restoring by position would put the keyboard on the wrong row.
- **The restore must not create a selection where there was none.** It uses
  `QItemSelectionModel.SelectionFlag.NoUpdate` — current is not selected.
- **Connection order.** `_restore_current_row` is connected to `modelReset` **before**
  `_ensure_a_current_row`, so the fallback only runs when the restore found nothing. Reversed, the
  fallback would win and the fix would do nothing while its test still passed if that test asserted
  the wrong thing.

## §3 · `T-193` — the playlist picker showed two of sixteen

**Symptom 1, fixed and measured.** `EntryTable.sizeHint` derives its height from the model's row
count, capped at `VISIBLE_ENTRIES: Final = 8`.

| Entries | Table height |
|---|---|
| 2 | 62 px |
| 4 | 122 px |
| 8 | 242 px |
| 16 | **242 px** — previously the same as 2 |
| 200 | 242 px |

**The criterion is measured against the row count, not against a constant**, so a changed cap moves
the assertion with it rather than the assertion pinning the old value.

**Symptom 2 is not fixed, and `T-204` owns it.** The maintainer's reproduction —
*"I think it removed the video from being downloaded, but it made everything inaccessible"* — traces
to `EXPANDED_ROLE` returning `None`, which the delegate reads as *not a playlist, draw no
disclosure*, whenever a row is not `committable`. **Nothing closes an open panel when that happens**:
`close_panel` is driven by the dialog's own `_expanded` state and `remount_panel` closes only when
the row's index is invalid. **So the panel outlives the control that dismisses it.**

**Acceptance criteria 3 and 4 are `T-204`'s.** Criterion 4 requires the stuck state be reproduced in
a failing test *before* it is fixed; that reproduction has not been written, and `T-204` carries it
as its first deliverable.
