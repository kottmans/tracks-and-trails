## `T-115` — `T115-R1` corrected

Your finding was exact. Add admitted every fresh row the moment it was saved, then began the
probed row's retarget and admitted it from *that* completion. The probed row is persisted first
and therefore holds the lowest `queue_position`, so with a pool of one the second URL started
while the head of the queue waited.

**Admission is now one decision**, taken after the retarget settles, probed id first. Your
regression passes. A refused retarget still admits the rest of the paste, because those rows carry
no stale request of their own — stranding them would be `T-115` again for everyone who probed
first.

Insertion order is the durable order: `queue_position` is allocated `MAX + 1` inside the insert
transaction and the probe was submitted before the batch. Sorting by a read-back position would
put a database read in front of a GUI callback for an ordering the writes already fixed
(`ARC-005`).

**`T115-R2`:** `compose()` no longer claims it starts nothing, and the phase launcher no longer
says the queue has no route that drains it. The priming loop is gone — and with it, the two
launchers turned out to be **the same program under two names**, so they are one. All twelve phase
tests pass on the Add route alone, which is better evidence than before.

**`COORD-R12`:** the `TASKS.md` In Review note and the `STATUS.md` snapshot are rebuilt from your
verdict, and the superseded `T-115` narrative is marked historical rather than left as a live
heading contradicting the one above it.

Three mutations on the correction; all three killed.

## `UX-003` — nothing enters the queue unprobed

**A maintainer decision, recorded in `ai/DECISIONS.md`.** Worth reading before the tasks, because
all three implement it.

Probing was optional and covered the **first URL only**. Everything else a user pasted was
persisted `QUEUED` having never been looked at — no title, no duration, no thumbnail until it
reached the front. Nothing decided that; it fell out of Phase 1's pool of one.

It is affordable because **the add-time probe is not load-bearing**: `downloader/worker.py` —
*"A download session probes first, so DRM and ffmpeg are caught before any bytes move."* Nothing
downstream reads the earlier result, so probing at the door costs one round trip and cannot go
stale.

The decision records what it costs: `REQ-018`'s retry splits by cause (a download failure still
sits in the queue; a URL that never probed has its retry in the dialog), and a long resolve is not
durable.

## `T-116` — the metadata lane

`_has_capacity()` counted every session against `REQ-013`'s single limit, so **a probe took a
download slot**. Measured: limit of three, twenty URLs added, the twentieth probed only after the
nineteenth had finished downloading. Tolerable while probing was a button; under `UX-003` it means
pressing Add stalls the transfers already running.

Two lanes now. `REQ-013` still governs downloads and nothing else.

- **The fill loop takes the next job it *can* start**, not the next job. Stopping at the first
  refusal is correct with one budget and starves a lane with two.
- **`admit()` takes a kind.** The only public route to a probe was `start()`, which raises when the
  lane is full — useless when a paste of twenty probes twenty.
- A refusal names its lane, so a caller refused a probe is not handed three running downloads as
  the reason.

Six mutations; all six killed.

### The thing I would check hardest

**`DEFAULT_PROBE_CONCURRENCY` is 4 and is not configurable.** I fixed it in code and said so:
`REQ-013` is what a user throttles to protect their connection, and a second spinbox for something
nobody has asked to tune is capability without a reason. If that is wrong it is a decision to take
rather than a default to leak, and it is cheap to change now.

## `T-117` — the thumbnail URL

`MediaInfo` has carried one since `T-016` and nothing stored it, so the address died with the
dialog that probed for it.

**This is the first migration after the initial schema.** The runner had never applied a second
script to a database holding rows. `T014-R4`'s frozen-fixture gate refused the build until v2's own
bytes were captured, which is the only moment they can be; `v2.sql` seeds **both** states of the
column so a later migration cannot silently lose one.

- The probe writes the title and the URL in **one revision**, asserted on the number of writes as
  well as their content.
- `NULL` is the answer for both "not probed" and "the site offered none"; `status` distinguishes
  them and neither is an error.
- No backfill. A v1 row was never asked, and inventing a value would be a claim the probe never
  made.

Six mutations; all six killed, two against the migration itself.

## `T-118` — the add dialog as a staging list

The largest change, and the one I most want read. Pasting resolves every line; *Add to queue*
commits what resolved. The Probe button is gone, and with it the route to queueing something
unread.

`ui/staging.py` holds the state machine, **Qt-free**, so its rules are asserted without a
`QApplication` (`ui/reveal.py` is the precedent). 21 tests there, 40 in the dialog.

### Six defects this found, none of them in the rewrite itself

1. **`T-115` came back in a new shape.** Under `UX-003` a job is probed *before* it is queued, so
   what a previous run leaves behind is `READY`, not `QUEUED`. `compose()`'s startup admission
   filtered for `QUEUED` only — it would have found nothing and drained nothing. **The phase proof
   caught it.** `queued_job_ids` now admits both, and the docstring says why both are safe for the
   same reason rather than because they look similar: recovery has already moved everything in
   flight to `FAILED`, and neither status is reachable by a job a worker was holding. `RUNNING`
   stays absent.

2. **A paused queue refused to read URLs.** `start()` has admitted a probe on a paused queue since
   `T080-R1`; `admit()` never had that rule. Invisible while probing was a button, immediately
   fatal once the dialog probes through `admit`: every pasted URL stayed unread and the dialog had
   nothing it could ever offer to queue. **The phase proof caught this one by hanging.** The rule
   is now one predicate that admission, the fill loop and `start()` all read.

3. **`done()` disposed of the wrong set.** It used "rows that will never be committable", which
   excludes a `READY` row nobody committed — the case that looks like success and is not. Closing
   on such a row leaves a download in the queue the user never added.

4. **`statusMessage` was focusable and undeclared**, which is `T016-R4` exactly. Caught by the test
   that compares the declared chain against *every* focusable widget rather than a filtered subset.

5. **`bytes_total` was never persisted for a pre-probed download.** It is written only by a progress
   message that *moves* a stage, which was complete while every download began at `QUEUED` and was
   moved to `RUNNING` by its first downloading message. `UX-003` starts a download from `READY`, so
   `start()` has already moved it and no message moves anything — **every download would have shown
   an unknown size**, and `T-014`'s stored total would have been a column nothing ever wrote. Now
   persisted once, when a total first becomes known, rather than on every progress message.

6. **A Windows-only focus-chain table still encoded the old rule.** `tests/ui/test_windows_desktop.py`
   is skipped on Linux, so no amount of local test-running would show it — **`mypy --platform win32`
   caught it**, because it type-checks tests as well as source. Two of its four state rows were
   wrong in substance, not just in name: "a URL typed" previously made Add available, and under
   `UX-003` typing a URL does not make it addable, being *read* does.

### The decision I most expect you to contest

**Withdrawal is now `remove`, not `cancel`, and that reverses `T016-R1`.**

That ruling kept a withdrawn row as `CANCELLED` — "an honest record of something asked for and
withdrawn". It was: the user had pressed *Probe* on that URL. `UX-003` removes that intent, because
a row is written only so the manager has a job id to probe. A queue of `CANCELLED` rows for URLs
somebody typed and thought better of is litter, not a record.

It is also the only route that works. `ARC-004` has `FAILED → QUEUED` and nothing else, so
cancelling a row whose probe failed **raises** — the exact case `UX-003` says must not reach the
queue. A rule needing two disposal routes, one unreachable for the commonest case, is the wrong
rule. `remove` cancels a live session first and deletes only once it has ended, so `T016-R2`'s
guarantee is unchanged.

If you disagree, the alternative is adding `FAILED → CANCELLED` to `ARC-004`, which is a state
machine change and yours to rule on.

### Other things worth your attention

- **Resolution is debounced** (`DEFAULT_RESOLVE_DELAY_MS = 400`). "Pasting starts the work" is
  unambiguous for a paste and impossible for typing — a probe per keystroke spawns an interpreter
  per keystroke. `resolve()` is public so tests drive it directly rather than on wall-clock time,
  and one test builds the dialog with a zero delay to prove the timer really calls it.
- **A plain item list, not a widget per row.** A paste is unbounded and this application is public;
  one `QWidget` per row makes five hundred URLs a five-hundred-widget layout pass. A test asserts a
  five-hundred-line paste is one write and stays inside `NFR-001`'s budget.
- **Per-row actions are a context menu**, not the buttons the mockup drew. `CustomContextMenu`, so
  the menu key and Shift+F10 reach them (`NFR-005`) — the same reason `T-086`'s file actions use
  it. This is a divergence from the approved mock and I am flagging it rather than hoping.
- **Every row is filled from the first frame** with a tile derived from its URL. `hash()` is
  deliberately not used — it is salted per process, so the same URL would get a different tile
  every launch.

## Tests that were passing for the wrong reason

Six this session, which is why I am listing them rather than burying them. Three were found by the
mutation battery on the task they belonged to; three by a battery on a *later* task.

- **`eq=False` on `Row`.** A mutation removing it **survived all 19 staging tests**, so the
  paragraph justifying it described a bug the code no longer had — I had fixed it while writing
  `reconcile` and left the justification standing. The docstring now says what is true and a test
  pins the semantics at the level the claim is made.
- **A probe that never reached the fill loop.** `test_a_waiting_download_does_not_hold_up_a_waiting_probe`
  admitted its probe while the manager was running, which starts it directly — so the loop the
  test is *named for* was never involved, and it passed with the loop's filter removed.
- **Two `T-116` tests parked a probe behind pause**, which stopped parking probes once pause became
  kind-aware. Both would have passed while proving nothing. Both now saturate the probe lane, which
  is the only thing left that can park a probe.
- **`T-118`'s commit filter rested on a downstream refusal.** A mutation making Add commit *every*
  visible row survived: the test used a batch where everything failed, and `retarget` refuses a
  `FAILED` job, so the commit aborted and `queued_job_ids` was empty either way. That is `T081-R4`'s
  shape exactly. A mixed batch — one readable URL, one not — makes the two answers different
  numbers.
- **`T115-R1`'s admission barrier could not fail.** `FakeStore.update` completed inside the call, so
  every retarget settled before the next statement ran and a barrier behaved identically to none.
  The store can now hold writes open. It took two attempts: with the preset unchanged, `retarget`
  skips the write entirely (`T075-R1`) and calls back synchronously, so deferring deferred nothing.
- **`admit` versus `start` for a probe was unobservable** until a paste exceeded the probe lane.
  Chasing that mutation found a real defect: rows were marked `PROBING` the moment `admit` returned,
  though `admit` *parks* when the lane is full — a paste of five hundred showed five hundred rows
  saying "Reading" when four were. Hence `RowState.WAITING`.
