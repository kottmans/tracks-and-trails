## `T111-R1` — the route the form's own docstring already promised

`_build_form` has always said the seven options have an editor and that a second set of controls
here would be two screens answering one question. That reasoning was right and only half-built:
nothing in `preset_manager.py` ever opened the other screen, so on a **saved** preset a user could
edit name, selector and template and could not edit media kind, codec, quality, remux, recode,
thumbnail, metadata, chapters or subtitles — most of what `T-109` put in a preset.

**What was added:** an `Options…` button (`EDIT_OPTIONS_NAME`) between *Set as default* and *Save
changes*, opening the **same `OptionsDialog`** the one-off path uses, titled `Options for {name}`.

Three decisions inside it worth your attention, because each could reasonably have gone the other
way:

- **No `save_preset` sink is passed**, so *Save as preset…* is not drawn (`UX-005` §5 — nothing
  offered that would be refused). A creation route inside the editor of a preset is a second way to
  create one on the screen whose job is managing them, and it leaves two presets where the user
  meant to change one.
- **The form's unsaved contents are deliberately not merged in.** `Options…` edits the *stored*
  preset; `Save changes` edits the form's. Combining them silently would make the result depend on
  which control the user touched last.
- **Name and default identity are re-stated on the way back** rather than trusted:
  `replace(dialog.result_preset(), name=preset.name, built_in=False)`. `OptionsDialog` neither
  edits nor returns a name of its own today, but this is the write path.

A built-in opens nothing and writes nothing — `_delete`'s clause and `§8`'s, applied identically.

**Asserted by** (`tests/ui/test_preset_manager.py`, six new cases): the stored-fields case drives
the **real** `OptionsDialog` widget — only `exec()` is intercepted, because a modal event loop
hangs a test — and asserts on the `Settings` handed to the sink, so a route that opens the screen
and writes something else fails.

## `T111-R2` — the policy was enforced everywhere except where a file enters

`add_preset` and `update_preset` refused a taken name. `_presets_from` validated each entry's
*shape* and nothing about its name, so your probe was correct: a hand-edited preset named
`Audio only (MP3)` loaded with `problem=None`, drew two rows of one name, and `preset_named`
answered with the built-in while the saved row held a different selector.

**Refused rather than disambiguated, and that is the stated policy applied rather than a new one.**
`add_preset` refuses a name the *user typed*; `free_preset_name` disambiguates one *nobody
proposed*. A name in a hand-edited file is the first of those — typed in an editor instead of a
dialog. Renaming it here would also be this module quietly rewriting a file the user wrote by hand,
which is what `ARC-008` exists to report rather than do.

Two ordering choices, both deliberate: **built-ins are checked first**, so a saved entry cannot
shadow one that ships; **earlier entries win**, so the file's own order decides and the answer does
not depend on which duplicate was written last.

**Asserted by** (`tests/unit/test_settings.py`, four new cases): built-in shadow, saved/saved
duplicate with the earlier entry winning, a collision not costing the entries around it, and an
anti-vacuity case proving a clean file still reports nothing.

## `T111-R3` — the test bypassed the stack the defect lives on

Corrected as you specified: `QTimer.singleShot(0, self._show_preset_manager)`, the same shape
`open_options` uses.

The **existing** test needed changing too, and that is worth flagging rather than burying: it
asserted the callback fired synchronously from `setData`, so it encoded the defect. It now asserts
the opposite — nothing opens inside `setData` — and the new case drives the real combo through
`commitData`, asserts nothing opens underneath it, drains `DeferredDelete`, and reopens the row to
prove the editor was reaped rather than left dead.
