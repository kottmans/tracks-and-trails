Five assertions this session measured a proxy rather than the property

  • A hover test drew through QApplication.style() with no widget, so it measured the platform style.
  • A palette test asserted the global palette held the row tint — it encoded the defect it was written for.
  • The chip's terminal test compared two rows that drew no chip at all, so both crops matched because nothing was in them.
  • The spin box test asserted arrow-coloured pixels existed. A solid block satisfies that, and a solid block is what shipped.
  • The toolbar test built a bare QToolBar, which paints no gradient, and compared window against window.

Four were mine and three passed while the defect was on screen. ai/TESTING.md §13 already forbids a test that passes for a reason other than the one it names; what these share is narrower and worth naming — they asserted that something was drawn rather than what was drawn. Presence is not shape, and a mutation is what tells them apart.

The gates that are left

One is a machine running unattended for five hours. The other needs a person who did not write the code. Neither is development work, and nothing depends on the order — the commit they both needed exists.

  1. Gate 1 A clean 60-run Linux soak Not started

    T-128's crash reproduced at 2 in 39 full-suite runs. The corrected teardown has to be shown to have removed it, and the number is sized against that baseline rather than picked: if nothing had changed, a clean sixty has probability 0.042. Thirty-nine only reaches 0.128 — which is why re-running the original soak at its own size would not clear the bar it set.

    baseline 2 / 39 runs = 5.1% P(0 crashes | unchanged) 39 runs 0.128 60 runs 0.042 <- the bar 90 runs 0.009

    tools/soak.sh is the instrument. It separates a process death — exit 139, which is what T-128 was — from a test failure, because collapsing the two would hide whichever is rarer. Roughly five hours at ~6 minutes a run.

  2. Discharged Windows evidence on 3dff8d2 Done

    OPS-010 puts the full Windows suite on STARBASE for every push, so this costs a commit rather than a decision. It is owed because T-129 changes how Qt renders, and the style that renders it is platform-specific — the group-box metric in particular has only ever been measured on Linux.

    The ordering constraint is spent. Windows evidence has to name a head, which is why this waited on a commit; 3dff8d2 is pushed and run 30954720566 passed all five jobs against it, windows desktop and frozen windows included, with the Windows leg on STARBASE rather than hosted minutes.

    It is listed here but it is not a phase criterion. T-130 is a Phase 3 task; the evidence is owed to it. Criterion 5 — no worker outliving exit, on both platforms — was met separately by the corrected gate at 8d1b01c.

  3. Gate 2 Criterion 6 — an independent phase exit review Not requested

    Every deliverable is approved and every review finding is closed. What is absent is the phase sign-off, which Phase 0 and Phase 1 each required and neither could self-certify: AGENTS.md §3 puts it with a reviewer who is not the implementer.

    Expect the table to move. Phase 1's exit review found two wrong rows; Phase 2's first attempt found two more — both times by rebuilding the table against the repository rather than reading the claim. This table is rebuilt before it is submitted, not re-read.

The overnight segfault, diagnosed

Two runs in thirty-nine died. The answer came from the core dumps, which were still on the machine.

A timer fired into a QObject that had already been freed

systemd-coredump had kept both crashes. gdb gives what a stack could not: the faulting instruction is receiver->d_ptr->threadData, and the receiver's memory was already recycled — its vtable slot held a value that is not even 8-aligned. A use-after-free, not corruption, which is why both runs died at the same test count.

0x556292ed2c90: 0x00005567c4c40522 <- vtable slot, not 8-aligned 0x556292ed2c98: 0xf40d334f663faf5d <- d_ptr, noise

The failing test, named from the traceback rather than the dot count. The Python stack points at a fixture teardown, which runs after pytest prints the progress character — so 97 dots means test #97, test_a_ready_job_starts_a_download_at_running, not #98 as the task had inferred. It is the one test in that file with a live worker, a live ResultPump and a live log thread: exactly the thread set both logs show.

The precondition, reproduced deterministically. is_idle answers a question about work — it says nothing about the manager's own poll timer, which stops on a later tick. Five teardowns polled it and dropped the manager inside that window.

The correction is a shared drain() that waits for the timer as well as the work, at all five sites, plus a detector that turns Qt's cross-thread timer warning into a test failure naming the test that caused it. The detector has never fired in this suite — it guards the mechanism that would otherwise surface as a segfault several tests later.

What OPS-007 now says, and why it was re-ruled twice in one day

A risk acceptance is only as good as the measurement under it. This one's measurement changed, then changed back.

Morning. OPS-007 accepted T-074's access violation because 361 attempts produced zero events, and said in as many words that a recurrence reopens it. T-128 reproduced something in the same subsystem at 2 in 39, so the premise fell and the exit was made to wait on diagnosing it.

Afternoon. The diagnosis says those two crashes were not recurrences of T-074's fault — they were the harness dropping a Qt object incorrectly. So the premise is arguably intact rather than broken, and the prerequisite was replaced with the narrower thing that can actually be measured.

One correction to the recommendation that produced this ruling. It first proposed confirming on Windows that the corrected teardown ends T-074's recurrences — but there are no recurrences on Windows to end, and more green runs there would only re-accumulate the very evidence that produced OPS-007. The confirmation is on Linux, where there is a baseline. Windows is a passive watch, and its value is asymmetric: a recurrence would rule the harness fix out as T-074's cause, while continued silence adds nothing.
