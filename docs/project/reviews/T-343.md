### Implementation assessment

- `present()` installs the rule before showing the main window. Off Windows the
  helper installs nothing. Repeated installation for the same owner returns the
  existing filter.
- The native entry point checks the event type before interpreting its pointer,
  converts the real PySide `VoidPtr` to an address, and reads only the needed MSG
  fields. The native Windows test checks their offsets and sizes against
  `ctypes.wintypes.MSG`. Both WM_CLOSE and masked SC_CLOSE are covered.
- Target-handle filtering and the initial ownership check preserve other message
  routes. An unblocked close passes to Qt. An owned dialog closes through its own
  normal close/done path; the main window's close event still saves geometry and
  starts orderly shutdown. The independent composed checks below exercised this
  with the actual Add URLs and Preferences classes.
- Refusing a close while Add URLs is saving is consistent with its existing
  persistence rule. The filter asks once and consumes the gesture; it does not
  close over an unsettled commit. Requiring another gesture afterwards is an
  acceptable implementation choice within the ruling, without adding a deferred
  shutdown policy. Discarding unadded text uses the existing normal-close policy.
- The filter reaches its owner through Qt parenting and retains no QWidget
  attribute. The destruction connection retains the application and filter,
  and explicitly unregisters the filter when its owner is destroyed. The current
  tests reject restoring eager or lazy owner references and removing cleanup.

### The Qt documentation judgment

[Qt documents automatic removal in the native-filter destructor](https://doc.qt.io/qt-6/qabstractnativeeventfilter.html#dtor.QAbstractNativeEventFilter).
That describes a destructor contract. It does not establish that destroying the
QObject side of this PySide multiple-inheritance object invokes that destructor
at the required time. The retained Windows failure demonstrates that dispatch
still reached an unusable Python filter after owner destruction; it does not
trace the C++ destructor itself. The precise underlying binding/lifetime cause
remains unproved.

Explicit removal tied to owner destruction, backed by native Windows execution
after that destruction, is the appropriate boundary here. The current correction
does not depend on deciding whether Qt's C++ contract or the binding's object
lifetime caused the earlier behavior. Likewise, the old owner reference was a
forbidden shape; the earlier collection crash alone did not prove its causation.
No source correction is requested on that attribution question.
