| ID | Severity | Blocks approval | Finding and evidence | Disposition/status |
|---|---|---|---|---|
| T322-R3 | High | Yes | `RemoveApplicationData` (`packaging/tracks-and-trails.iss:182–192`) discards every deletion result, and the completion handler at line 287 always reports removal. There is no running-application guard. A running application can keep its SQLite database open or recreate settings/geometry after the selected cleanup; an unrelated file lock or denied deletion also goes unreported. The ticked choice can therefore leave the user's queue/settings in place while uninstall reports success. | **Open — T-322 correction.** Establish quiescence before removal and check the named cleanup outcomes, accounting for already-absent files. If cleanup cannot complete, give an accurate actionable result without claiming success for that choice. Preserve user-owned files and the unticked/silent defaults. Verify running-app and locked-file cases on Windows. |
| T322-R4 | Medium | Yes | `InitializeUninstall` uses `Exec(..., ewNoWait, ...)` at line 277 and immediately aborts the first run after process creation succeeds. Inno holds the same `unins*.dat` with exclusive access during this callback. A second invocation can reach its initial exclusive open before the first releases the file, then fail after `Exec` has already returned true. The fallback handles only failure to create a process; it cannot recover this child-initialization failure. | **Open — T-322 correction.** Sequence the replacement invocation after the first has released its uninstall log, with an observed completion/failure contract. Verify under forced scheduling delay that the second run succeeds or reports failure without losing the uninstall action. Avoid a fixed sleep as the synchronization mechanism. |

The lock sequence is directly visible in the pinned
[Inno Setup source](https://github.com/jrsoftware/issrc/blob/is-6_7_3/Projects/Src/Setup.Uninstall.pas):
`OpenUninstDataFile` uses `fsNone` (lines 356–367); the second phase retains that file through
`InitializeUninstall` and releases it in final cleanup (lines 616–620, 680–687, 803–808). A new
invocation opens the log during its own startup. This establishes a race in the code; its frequency
on STARBASE is unmeasured. `{uninstallexe}` names the installed executable, so the two invocations
do not share the temporary directory hypothesized in the submission.

Inno's [AppMutex documentation](https://jrsoftware.org/ishelp/topic_setup_appmutex.htm) explains
that detecting a running application requires a named mutex created by the application and checked
by the installer. This project declares no AppMutex and instead uses an exclusive file for its
single-instance guard. An equivalent correctly synchronized guard is acceptable; the finding does
not mandate replacing that existing instance-lock design.

The named deletion list preserves the original T322-R1 boundary under `{app}`. The packaging tests
pass but inspect declarations, not executing uninstall processes or successful file deletion.
The maintainer's reported unticked/ticked Sandbox observations remain useful normal-path evidence;
they do not cover these failure cases. The scripted candidate Sandbox gate and its preservation
checks must run on the corrected release candidate under the accepted T-039 cadence.

The intermediate mypy failure is historical, and both head type checks pass. Shared validation,
remaining Windows limits and exact test results are in the
[session review](T-337.md#2026-09-14--initial-review-of-the-session-changes).
