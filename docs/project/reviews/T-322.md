| T322-R1 | Critical | Yes | `packaging/tracks-and-trails.iss:119` uses `Type: filesandordirs; Name: "{app}"`. This recursively deletes the **whole chosen directory**, including files absent from the installation log. A user who places downloaded media there, or installs into an existing directory, loses that data on uninstall. The adjacent claim that only installer-created files are removed is false, and the uninstall prompt promises downloaded files are kept. | **Open — correct in T-322 before distribution.** Remove the recursive deletion of arbitrary contents. Let Inno remove the files it installed; any additional cleanup must name exclusively application-owned artifacts. Verify that a pre-existing sentinel and a user-created media file survive, while installed files and shortcuts are removed. Reconcile T-039's definition of leftovers with that ownership boundary. |

Inno's own [UninstallDelete documentation](https://jrsoftware.org/ishelp/topic_uninstalldeletesection.htm)
defines `filesandordirs` as recursive deletion and warns against wholesale cleanup
of the application directory because it can destroy users' files. This finding
rests on the executable installer declaration and its documented semantics; it
does not claim a destructive test was run on a user's machine.

The retained Sandbox test only installs into an empty default directory. It
therefore cannot exercise this case. Its five-file user-data count is outside the
install root and provides no protection for files inside it.

The numeric version derivation, per-user default, opt-in desktop shortcut, absence
of a taskbar option and committed artwork dimensions agree with the stated
rulings. Their source tests pass. The task's workflow and SmartScreen evidence
remain open; [T-324](T-324.md) separately identifies the incorrect upload path.

Shared validation is in [the batch record](phase-5-second-batch.md). No source fix,
task closure or release approval is performed by this review.
