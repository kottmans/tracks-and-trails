### Codec reproduction and correction boundary

The [MP4 Registration Authority object-type registry](https://mp4ra.org/registered-types/object-types)
assigns hexadecimal `69` and `6B` to MPEG audio types outside AAC, and `E1` to
13K Voice. [RFC 6381 §3.3](https://www.rfc-editor.org/rfc/rfc6381.html#section-3.3)
describes the object-type component of `mp4a` codec strings; its
[§3.6 examples](https://www.rfc-editor.org/rfc/rfc6381.html#section-3.6) explicitly
include `mp4a.E1`. The first token is consequently insufficient.

Ran this path through the installed yt-dlp parser, the real projection adapter
and the Qt model; no network request or production file was involved:

```bash
QT_QPA_PLATFORM=offscreen .venv/bin/python - <<'PY'
from PySide6.QtCore import Qt
from PySide6.QtWidgets import QApplication
from yt_dlp.utils import parse_codecs
from tracks_and_trails.downloader.ytdlp_adapter import project_format
from tracks_and_trails.ui.format_table import AUDIO_CODEC_COLUMN, FormatTableModel

app = QApplication([])
for raw in ('mp4a.40.2', 'mp4a.69', 'mp4a.6B', 'mp4a.E1', 'mp4a.future'):
    entry = project_format({'format_id': 'review', 'ext': 'm4a', **parse_codecs(raw)})
    model = FormatTableModel((entry,))
    index = model.index(0, AUDIO_CODEC_COLUMN)
    print(raw, model.data(index), model.data(index, int(Qt.ItemDataRole.ToolTipRole)))
PY
```

At the reviewed head all five display values were `AAC`; each tooltip preserved
its input. The positive AAC example is correct. The remaining four establish
the defect and fallback gap. This proves an accepted-input path, not the
prevalence of these codecs on a particular live site.

### R1 — why the narrower AAC table is sound but the MP3 label is not

The [MP4 Registration Authority](https://mp4ra.org/registered-types/object-types)
registers `69` against ISO/IEC 13818-3 and `6B` against ISO/IEC 11172-3; it does
not restrict these entries to Layer III. FFmpeg's own
[object-type table](https://ffmpeg.org/doxygen/trunk/isom_8c_source.html)
maps both MP2 and MP3 to `0x69`, further demonstrating the ambiguity. These are
primary sources for the correction boundary, not a demand for a larger codec table.

An independent local probe using **FFmpeg 8.1.2** encoded one second of synthetic
silence as MP2. It produced a fragmented MP4 initialization segment with an
`esds` object-type byte of **`6b`**. The first encoded audio frame was
**`fffd8404`**, whose layer bits are **2 (Layer II)**. Captured command:

```text
ffmpeg -hide_banner -loglevel error -f lavfi -i 'anullsrc=r=48000:cl=stereo' -t 1 -c:a mp2 -b:a 128k -f dash /tmp/t306-rereview/mp2.mpd
```

The generated manifest itself advertised the more specific `mp4a.40.33`, which
the corrected application safely leaves raw. To test the coarser identifiers,
made **derived in-memory manifest variants** replacing that codec attribute with
`mp4a.69` and `mp4a.6B`, then called yt-dlp's `InfoExtractor._parse_mpd_formats`,
`project_format`, and the real table model. No live source or network request was
involved. Observed:

| Manifest codec | Projected codec | Display | Tooltip |
|---|---|---|---|
| `mp4a.40.33` | `mp4a.40.33` | `mp4a.40.33` | absent |
| `mp4a.69` | `mp4a.69` | **MP3** | `mp4a.69` |
| `mp4a.6B` | `mp4a.6B` | **MP3** | `mp4a.6B` |

Thus the remaining problem is an accepted-input path that assigns a more
specific codec than the input establishes. It is not evidence of prevalence on
a particular site. The raw tooltip remains a workaround, so the severity stays
Medium. Keep the conservative handling of other MPEG-4 audio object types;
mapping all `40.*` values to AAC would reintroduce the original defect class.
