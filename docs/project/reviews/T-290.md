### Lifecycle reproduction

A fresh SettingsDialog with the normal update/revert callbacks starts with
`Get a newer yt-dlp`. Calling its public busy API with True then False leaves
an enabled button reading `Update to the latest version`.

A second probe opened Settings through MainWindow with a local YtdlpService
subclass whose refresh emits the real busy/report signals without network
or a child process. The same final-label assertion fails. Production
`YtdlpService._on_resolved` and `_on_failed` both call `_set_busy(False)`,
and MainWindow forwards `busy_changed` to the open screen. Thus the trigger
is an ordinary opening check as well as the end of an explicit operation.
The two probes returned **1 failed** each, at the old-label comparison.
