### Reproductions and scope

**R1:** A `MainWindow` over one QUEUED job, shown with its queue row selected,
was sent the keyboard-reason `QContextMenuEvent` through the viewport using
`tests/ui/test_row_verb_wiring.py::_press_the_menu_key`. The visible QMenu's
actions were exactly `['↑', '↓', 'Cancel', 'Remove']`. That helper exercises
Qt's dispatch and the production connections. An initial attempt used
`QTest.keyClick(Menu/Shift+F10)` and opened no menu under offscreen; that is the
plugin translation limitation already documented by the helper, not evidence
that native keyboard menus fail to open. No native key translation is claimed.

**R2:** Created two QUEUED jobs with `playlist_id='list-1'`, common playlist
title, and positions 1/2. Read the header's real visual rectangle, initialized
`QStyleOptionViewItem` from the view, and clicked the delegate's menu-zone
center with `QTest.mouseClick`. `item_menu_requested` emitted **list-1**, but
no visible menu appeared. Repeating with two ungrouped jobs emitted **0** and
opened a menu. This checks the pointer route and supplies a positive control.

**R3:** Built requests through `presets.to_request` from AUDIO_MP3 with the
following valid codec/quality replacements. Opened the queue's real Options
dialog, accepted unchanged, and captured the request passed to manager.retarget.
All other request fields were equal:

| Codec | Original quality | Quality after unchanged OK | Result |
|---|---|---|---|
| MP3 | `0` (VBR) | `320` | Failed preservation |
| MP3 | None | `320` | Failed preservation |
| MP3 | `96` | `320` | Failed preservation |
| AAC | `3` | None | Failed preservation |
| MP3 | `192` | `192` | Passed control |

These are accepted domain values, including values custom presets can carry;
they are not malformed requests. The shared editor behavior predates this
task, but the new queue route promises lossless editing of those requests and
must account for the editor's domain. The unchanged-options test's video-only
request disables the entire audio group, bypassing both lossy branches.

### Inverse, signal ownership and dialog checks

`preset_of` itself correctly copies the Preset/DownloadRequest field
intersection. Its round trip is lossless **for preset-owned fields**. A full
request additionally requires the caller to carry URL, destination and the
four connection fields; `_retarget_to` does this through `to_request` and
`with_connection_of`. An empty preset template resolves to the caller's
default, so preset → request → preset is intentionally not identity. The
new failure above occurs in OptionsDialog after this correct projection.

The registered probe-ID filter is correct in both listeners. Independent
tests emitted actual `media_probed`/`job_failed` signals for unrelated IDs
while an owned read was pending: neither consumed the pending ID, unstaged
anything, wrote a request nor opened a table. The no-formats and job-started
branches also passed through actual signals: status-bar explanation, no
dialog, no request write. **4 passed in 0.35s** for these signal cases.

A separate probe used a real DownloadManager and its fixture-replaying child
process, rather than replacing stage/unstage. The result opened FormatDialog;
the manager became idle, both `_reading` and `_staged` emptied, and no
`start_rejected` signal fired. This checks cleanup across the manager boundary.
The format table's existing merge refusal and completed-selection rules remain
shared. The main window is not itself modal; a FormatDialog here does not
introduce the modal-over-modal problem that motivated T-312's staging page.
