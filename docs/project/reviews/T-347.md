### Evidence inspected

The desktop report credibly distinguishes raising an existing window from opening a new one,
and preserves the implementer's two invalid probes and their corrections. The reported
false-to-true active-state transition supports trying WindowsRunner; it does not establish
the identity filter proposed around it.

The third match field is established by the upstream
[KRunner serialization definition](https://raw.githubusercontent.com/KDE/krunner/master/src/dbusutils_p.h)
and [KWin match construction](https://raw.githubusercontent.com/KDE/kwin/Plasma/6.6/src/plugins/krunner-integration/windowsrunnerinterface.cpp).
KWin's inspected current source agrees. A read-only query of the local running bus returned
`Match(s) -> a(sssuda{sv})`. Installed packages were `kwin-6.7.5-1.fc44.x86_64` and
`dolphin-26.08.1-1.fc44.x86_64`; the structural source comparison is not claimed as an exact
build-source audit of those packages.

[Qt's public Wayland interface](https://doc.qt.io/qt-6/qnativeinterface-qwaylandapplication.html)
does not offer a token-request method. However,
[Qt's desktop-services implementation](https://raw.githubusercontent.com/qt/qtbase/6.11/src/gui/platform/unix/qdesktopunixservices.cpp)
does request and forward tokens internally. Thus “no directly exposed token-request API” is
the defensible bound; failure of tokenless shell/D-Bus calls does not exhaust every route
through Qt. No alternative is claimed here to preserve selection or fix this desktop's case
without measurement.

### Independent reproductions

All adversarial probes used injected replies or offscreen Qt; none sent a close action to KWin.
Repository source and tests were not edited.

**Action confusion.** A fake Match reply contained a genuine `0_{other-uuid}` record whose title
included `1_{bbbbbbbb-0000-0000-0000-000000000002}`, followed by the genuine activation record for
that target. The info reply assigned the target pid 777 and `resourceClass=org.kde.dolphin`.
`window_of(777, ask)` returned `1_{bbbbbbbb-0000-0000-0000-000000000002}`;
`activate_command` retained that exact ID as the Run argument. The inspected
[KWin action enum](https://github.com/KDE/kwin/blob/Plasma/6.6/src/plugins/krunner-integration/windowsrunnerinterface.h)
defines ActivateAction first and CloseAction second. Its
[Run implementation](https://raw.githubusercontent.com/KDE/kwin/Plasma/6.6/src/plugins/krunner-integration/windowsrunnerinterface.cpp)
uses the integer embedded in the ID and calls `closeWindow` for CloseAction. This establishes a
wrong window action; no data loss or real desktop close is claimed.

**Event-loop stall.** With a temporary real file, a fast fake ShowItems/ListNames reply and a
250 ms delay in the fake isUrlOpen response, a 20 ms QTimer callback did not run before
`reveal_file` returned after **271 ms**. It ran only after event processing resumed. Production
uses `subprocess.run` at the same call site with a **10-second timeout per query**. This isolates
the new discovery wait from the pre-existing launch call.

**Ambiguity.** Supplying bus names `org.kde.dolphin-777` and `org.kde.dolphin-888`, with both
answering true, returns 777 without testing uniqueness. The inspected upstream
[ShowItems handler](https://raw.githubusercontent.com/KDE/dolphin/master/src/dbusinterface.cpp)
uses `attachToExistingInstance`; its
[recipient selection](https://raw.githubusercontent.com/KDE/dolphin/master/src/global.cpp)
starts at the active-window index and tests item visibility, not the lexically first folder-open
instance. With no active Dolphin it starts at the last candidate. The risk of raising a different
recipient follows from these distinct algorithms; it is a source-based inference plus a local
lookup reproduction, not a newly performed two-window desktop measurement. The upstream source
comparison is not an exact-source audit of the installed package.

**Probe preconditions.** Calling `precondition` directly produced:

| Supplied before-state | Case | Actual answer |
|---|---|---|
| No windows (`{}`) | 2, open elsewhere | `established: a window is open and none of them shows the folder` |
| One minimized unrelated window; target folder false | 4, target minimized | `established: a window shows the folder and is minimized` |
| Target folder true, active false, minimized true | 3, behind ours | `established: a window shows the folder and is behind ours` |

The third and fourth cases must be distinguishable on the same target. The retained tool also
minimizes every Dolphin window, including pre-existing operator windows, despite its message that
those are left alone. Correct that as part of making the instrument safe to rerun. The four-case
loop calls its own `show_items`/`raise_through_windowsrunner` implementation; the separately claimed
production-function measurements have no retained executable invocation/output. Repeating that
loop alone would therefore not verify a correction to the product function.
