### Reproduction and causality

Used the existing `_staged`, `_pick_a_pair` and `open_row_editor` helpers in
`tests/ui/test_add_dialog.py`, with a normal custom preset in the catalogue:
`replace(BUILT_IN_PRESETS[0], name="Metadata video", embed_metadata=True)`.
The catalogue order was the first built-in, that custom preset, then the
remaining built-ins. The first built-in was selected initially.

1. Show the resolved staging dialog, choose video `137` plus audio `140`, and Done.
2. Leave the row inheriting (`row.preset is None`), open its preset editor and focus it.
3. Deliver `QWheelEvent` to the batch `presetChoice` combo at its center, with
   `angleDelta=(0, -120)`, no buttons/modifiers and `NoScrollPhase`. It selects
   the adjacent custom preset without moving focus out of the row editor.
4. Process Qt events. The model answers `137+140 · embedding metadata`, but
   the still-open editor answers `currentIndex() == -1`, `currentData() is None`.
5. Call the production `commit_open_editor` lifecycle hook. The complete
   selection becomes None and `preset_for(row).format_selector` falls back
   to the batch selector, even though the inherited entry was never chosen.

The same sequence with `embed_metadata=False` passes: the role's name stays
`137+140`. With only the pre-correction `StagingModel.data` restored in an
isolated Python process, **both wheel variants pass**. The new role return
is therefore causal; this is not a pre-existing failure being reopened.
A first probe using the existing `choose_preset` helper found the same state;
the wheel probe then established a widget-event route to it.

The implementation's revived `createEditor` branch is necessary, but it
does not reconcile the other half of that lifecycle. `setEditorData` already
documents and handles an inherited label changing while the editor survives
a value-only refresh (T284-R3). The new composed entry needs that audit too.
This continues the integration pattern recorded above; no new process task
or policy addition is requested.
