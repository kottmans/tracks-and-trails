Microsoft's [SmartScreen developer guidance](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/smartscreen-reputation)
distinguishes file-hash reputation from publisher reputation, explicitly covers unsigned files,
and says EV no longer provides an automatic bypass. Its
[Artifact Signing FAQ](https://learn.microsoft.com/en-us/azure/artifact-signing/faq) likewise describes
reputation accumulating for a signed file, rather than a guarantee of no prompt. These are factual
corrections to the explanation, not a reconsideration of the maintainer's distribution choice.

Suitable replacement wording for the disputed explanation is: **This installer is unsigned, so
Windows may show a SmartScreen warning. If it appears, choose More info, then Run anyway. Each new
unsigned build must establish its own reputation.** Keep the existing observed prompt text and
the planned signing statement. Do not promise a particular download count, time or universal
Windows prompt behavior.

### Release claims and sequencing

- **The version has one source.** `__version__` is `0.1.0`, and Hatch reads that file. The tag
  checker accepts `v0.1.0`. The changelog extractor returns this release's body without leaking
  its heading; the updated subprocess test also retains the missing-version refusal. Replacing
  the old missing-file expectation is necessary now that CHANGELOG exists.
- **Both artifact names follow the actual build expressions.** Substituting `0.1.0` into
  `OutputBaseFilename` in the Inno script produces `Tracks-and-Trails-0.1.0-setup.exe`.
  `packaging/build_appimage.sh` produces `Tracks_and_Trails-0.1.0-x86_64.AppImage`. The workflow
  uploads these outputs and creates SHA256SUMS. This verifies names and wiring, not successful
  creation or digests of a yet-unbuilt 0.1.0 candidate.
- **The default Windows install description is supported.** The script uses lowest privileges
  and the per-user program directory; the prior Sandbox evidence and manual session support the
  ordinary double-click path. Explicit administrative `/ALLUSERS` remains an existing alternate
  invocation. Windows release packaging includes ffmpeg; Linux resolves the distribution's copy.
- **The Linux floor is consistent with the build.** The workflow uses
  `python:3.14-slim-bookworm`, matching the documented glibc 2.36 baseline.
  [Debian 12's libc6](https://packages.debian.org/bookworm/libc6) is 2.36;
  [Ubuntu 24.04's](https://packages.ubuntu.com/noble/libc6) is 2.39; and
  [Ubuntu 22.04's](https://packages.ubuntu.com/jammy/libc6) is 2.35. The examples therefore match
  the floor. This is a compatibility requirement, not a claim that every named distribution
  received a fresh candidate test. The system-CA and Linux-ffmpeg dependencies follow REL-007
  and OPS-001 and the existing packaging boundary.
- **The queue claims describe implemented behavior.** Reordering has named move actions and
  persisted ordering; crash tests kill a writer, reopen the database, and recover in-flight jobs.
  The claim concerns the queue surviving termination, not continued downloading while the app
  is stopped. The feature summary does not promise yt-dlp option parity. Narrator, macOS and
  single-instance/file-handler omissions remain disclosed.
- **Schema and support records are appropriate to the candidate.** Twelve migrations exist;
  `schema_versions/v12.sql` is present in `f22b2c7`, contains actual serialized job rows and is
  exercised by the historical-fixture test. No fixture regeneration is needed. SECURITY's latest
  0.1.x/minor support policy matches REL-003 and RELEASE; `main` remains the development line.
- **README and development-version changes belong to the stated later steps.** Their absence
  from this commit is accepted. The stale timing instructions are T328-R2, not evidence that the
  unpublished release should already be advertised as available.
