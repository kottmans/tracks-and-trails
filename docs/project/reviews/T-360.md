### Fetcher and retention assessment

The correction carries the accepted 2026-10-11
[OPS-001 amendment](../DECISIONS.md#amended-2026-10-11--the-pinned-build-is-kept-beside-each-release).
Upstream remains the first source. A `URLError`, including an HTTP error or wrapped network
failure, tries the release asset. Both sources feed the same unchanged SHA-256 check before
the archive is cached or extracted. A successful upstream response with the wrong bytes is
refused rather than silently replaced. Catching `URLError` beyond a 404 does not weaken the
pin: availability selects the source, while the digest still selects the accepted bytes.

Reading the version file as text works before package installation. Independent probes check
`0.1.0`, `0.2.0` and `0.2.0.dev17`, obtaining `v0.1.0`, `v0.2.0` and `v0.2.0`; a non-HTTP
`URLError` also takes the fallback in the correct order. The current `0.1.1.dev0` tree names
`v0.1.1`, which will not be published. This is the documented development-tree limit; T-358
already owns the version bump to `0.2.0`. The release workflow verifies the tag against the
source version before building, and a development tree has no retained release asset yet.

This reviewer independently fetched the
[`v0.1.0` asset metadata](https://api.github.com/repos/kottmans/tracks-and-trails/releases/tags/v0.1.0)
and downloaded its original ffmpeg archive into `/tmp`. GitHub and the downloaded bytes agree
on **76,400,239 bytes** and
`609245cc0a906c1423f2cdb96e27925302d375fe8024dcbc4b3f6aaf757a43ff`.
The retained local original hashes identically. Using the original pin read from `v0.1.0`,
the current production fetcher accepts those downloaded bytes through the fallback, verifies
the committed licence text and extracts both executables and seven DLLs into scratch storage.
This last probe simulates upstream failure; the public bytes themselves were downloaded
independently. The historical v0.1.0 fetcher has not been backported: rebuilding that old tree
can retrieve and preseed its verified archive manually.

The published v0.1.0 `SHA256SUMS`, independently downloaded, contains the installer and
AppImage entries only. It does not cover the newly attached archive. Its original source pin
and the re-hashed asset provide the byte verification above; this review did not alter the
published checksum file, upload anything or remove the local original.

### Release-workflow assessment

Windows acquisition remains an explicit digest-checked step before the release build. The
new artifact upload selects the fetched archive and uses `if-no-files-found: error`. The
draft job depends on both builds, downloads their artifacts, collects the archive beside the
AppImage and installer, refuses each missing class and includes the archive in `SHA256SUMS`.
`gh release create` receives those collected files and remains a draft operation.

This reviewer executes the **actual collection step's shell** from the parsed workflow in
scratch directories. With all three artifact classes, it exits **0** and the archive's exact
digest appears in `SHA256SUMS`. Without the archive, it exits **1**, reports `no ffmpeg archive`
and writes no checksum file. No release is created by these probes. The upload glob matches
the current pin's real filename. The new documentation accurately records where the copy
is kept and the requirement to retain it beside each release.
