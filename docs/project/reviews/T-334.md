### Independent reproduction

A temporary script uses the committed `FakeRepository` and `make_job`, a real
`DownloadManager`, and real spawned children. Before Start it calls
`admit_when_started("slow", SessionKind.PROBE)` for a durable QUEUED row and
`admit_when_started("fast", SessionKind.DOWNLOAD)` for a READY row. The probe waits
on a file barrier; the fast child emits valid `Succeeded` and `WorkerFinished`
messages. After the fast session has been released, the script opens the barrier.
The probe then emits valid `Probed` and `WorkerFinished` messages.

```text
after fast: False probing sessions ['slow']
after probe: False ready waiting ['slow'] signals [True, False]
after another Start: completed
```

The same script with only `_stop_when_drained` disabled, restoring the preceding
behavior, reports:

```text
after fast: True probing sessions ['slow']
after probe: True completed waiting [] signals [True]
after another Start: completed
```

Both runs shut down and reap their managers. The script is locally retained at
`/tmp/tt-phase5-review/queue_probe.py`; the sequence and output above are the durable
reproduction. No reviewed source was changed.

### Other conclusions

The delayed failure-write argument is sound for DOWNLOAD retries: the chain stays
present through the callback scheduling the retry, and its final removal rechecks
draining. The new tests exercise that ordering, including the 1.5-second delay.
That does not cover the durable-probe distinction above.

The amended mode is consistent with admitting additions while work remains;
it does not restrict admission to the instant Start was pressed. The defect is
what the implementation counts as remaining work. The stopped status message
over an empty queue is disclosed wording work, not another blocking defect here.
