### T308-R3 — an isolated canary demonstrated a persistent write

The tool always replaces `XDG_CONFIG_HOME`, but only supplies data/cache values
when the variables are absent. An existing `XDG_DATA_HOME` therefore remains the
source of `persistence.db.database_path()`. The call to `compose(qapp)` has no
explicit database override. It acquires that database's instance lock, opens it,
and calls `JobRepository.recover_interrupted()` before presenting any window.
The lock prevents collision with an active application; it does not protect an
inactive user's stored queue from a diagnostic launch.

Reproduction used only synthetic data and offscreen Qt:

1. Created a temporary directory, with `config`, `data` and `cache` children, and
   exported all three XDG roots to those children in the probe's parent process.
2. Opened the resulting `db.database_path()` with `db.connect`. Appended a `Job`
   named `isolation-canary`, with an `example.invalid` URL and a temporary output
   directory, then used `JobRepository.update(job.with_status(...))` through
   `PROBING`, `READY` and `RUNNING`. Closed the connection before launching the tool.
3. Ran `.venv/bin/python tools/t308_warning_stacking_probe.py` as a child with
   that inherited environment and a 20-second timeout. It created its own separate
   temporary config profile and completed normally. Reopened the original canary
   database and read the job.

Captured result:

```text
BEFORE running
TOOL EXIT 0
AFTER failed interrupted
CONFIRMED: tool rewrote the inherited data-root database outside its own temporary profile
```

For a control, copied the tool to a temporary file and replaced only its two
`os.environ.setdefault(..., profile)` calls with unconditional assignments.
Repeated the same procedure with a fresh canary database:

```text
BEFORE running
TOOL EXIT 0
AFTER running None
CONTROL: overriding inherited roots preserves the canary job
```

Both invocations still displayed and dismissed the missing-folder warning. The
repository tool was not edited. This establishes a persistent write outside the
probe's claimed isolation boundary; it is not a claim that the implementer's
reported native runs modified real data. No real user profile was touched by
the independent reproduction. The High severity reflects a diagnostic entering
and modifying the user's application state; irreversible loss was not demonstrated.
The cache root has the same inheritance defect, although this canary demonstrated
a database write rather than cache deletion.

### T308-R1 — what the supplied display record can support

The [submitted evidence](../evidence/2026-09-09-T308-warning-stacking.md) records
exposed and active dialogs, a transient-parent relationship, direct activation of
the OK button and an enabled main window. These are useful observations. Its
declared snapshot is a working tree based on `e47f17f` plus the `present()`
extraction; it does not identify the complete captured tree as `10e079c`.

The affirmative “centred inside” statement is not supported by its X11 numbers.
The tool prints `QWidget.geometry()` for both top-level windows: dialog
`(220, 150, 500, 260)`, parent `(480, 211, 960, 640)`. In desktop coordinates,
the dialog begins 260 pixels left of and 61 pixels above the parent. It is not
contained by that rectangle. Qt documents that a dialog remains a top-level
window even with a parent, and that a window's position is on the desktop;
unsupported window systems may instead return artificial positions.
[QDialog documentation](https://doc.qt.io/qt-6/qdialog.html#details),
[QWidget position documentation](https://doc.qt.io/qt-6/qwidget.html#pos-prop).
Thus neither treating the X11 tuple as parent-relative nor treating Wayland's
zero origin as a measured desktop position establishes the claimed containment.
This is an evidence correction, not a newly established product-positioning defect.

An independent offscreen coordinate probe confirmed that a parented message box
is top-level and that its geometry origin equals its global origin, rather than
its origin mapped into the parent. A separate modality check observed:

```text
before dismissal: parent enabled True modal active True
after dismissal: parent enabled True modal active False
```

The parent's enabled flag was already true while the dialog blocked it. Calling
the button's method directly likewise bypasses the physical input route. These
checks cannot replace the originally requested observation that the warning
appears above its parent, is findable/dismissible through normal input, and leaves
the main window usable. The outstanding work is that bounded check on the two
requested backends, not an expanded desktop certification exercise.
