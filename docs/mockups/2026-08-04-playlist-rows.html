A playlist as one row that opens

Sixteen rows from one paste is honest and unreadable. One row reporting item 4 of 16 is readable and hides fifteen downloads you cannot act on. This is the third option: one row that is a real row, and opens into the fifteen underneath it — so the connection between them is visible rather than remembered.

Filed against T-137. This supersedes nothing yet. UX-005 rows 9 and 10 currently record one job per entry, ruled earlier today; that entry is marked as under revision and will be rewritten to whatever is chosen here rather than quietly replaced.

The shape

Closed, then open

The same queue, one triangle apart. Closed, a playlist costs exactly one row — which is what makes a sixteen-item paste survivable next to ordinary downloads.

A child is a shorter row on purpose. It drops the format line — every entry inherits the group's — and the thumbnail shrinks, so the indent buys its width back instead of costing it. UX-005 §3's anatomy is intact; this is the same row with two lines instead of four.

The group's own progress

Sixteen segments, not one bar

The bar under a playlist is the thing most likely to lie, so it is drawn as what it actually knows: one segment per entry, filled as each finishes.

Segmented — proposed

3 done · 1 running · 1 failed · 11 queued

A failed entry is visible in the bar rather than folded into "not done yet". With one continuous bar there is nowhere to put it, and a playlist that quietly skipped a track would look identical to one that got everything.

Continuous — rejected

34%

34% of what? Sixteen files whose sizes arrive one at a time, so the denominator changes as it runs — the bar goes backwards when entry seven reports a total larger than the estimate. Job.progress already refuses to invent a percentage from an unknown total; this would reintroduce it at the group level.

What the verbs mean now

Two levels, and no verb that means both

VerbOn the playlist rowOn an entry
CancelCancel all — stops what is running and drops what is queued. Named differently on purpose: a button reading Cancel on a row covering sixteen files is the one most likely to be clicked by mistakeCancel — that entry only. The others carry on
PausePause all — holds the group without touching the rest of the queueAbsent. UX-001 has no per-job pause and this does not add one
RetryRetry failed, in the ⋯, and only when at least one failedRetry — the ordinary one
Open / Show in folderShow in folder opens the playlist's own folder. Open is absent — there is no one file to openBoth, once done
RemoveRemoves the group and its entries, with the count in the confirmation — DAT-005 §4's rule already says the question must name its own numberRemoves that entry from the group

Clear finished is the one that changes meaning. A playlist with three done and thirteen running is not finished, so it stays — but should the three vanish from underneath it? Proposed: no. A group is cleared as a unit when the whole of it is done, because an entry disappearing from a list the user opened specifically to watch is the opposite of what opening it was for.

What it costs to build

Three things this breaks, stated before they are discovered

Known, and none of them fatal

  • setUniformItemSizes(True) comes off. The queue sets it for speed, and it is a promise every row is the same height — which a two-line child and a four-line group break. T118-R10 is the record of what row cost buys, so this wants measuring on a paste of 150, not assuming.
  • The model flattens, rather than the view becoming a tree. A QTreeView would replace the list, the delegate and the geometry that four findings have already been spent on. A flat model that emits group rows and — when open — their entries, with an indent role, keeps every one of them.
  • The tab count needs a rule. Queue (2) above counts the playlist as one. Counting entries would read Queue (17) and make the number jump when a group is opened, which is worse; but "2" understates the work. Proposed: count rows as shown, and let the group's own 4 of 16 carry the detail.

Not listed because it is not new: entries must be durable, so the group survives a restart with its children and their states — the same REQ-020 promise every queue row already makes, applied to a row that owns others. That is a schema change, and on this project a schema change means a migration and a frozen fixture (T014-R4).

Recommendation

P1/P2, with the segmented bar and the count

It is the only one of the three shapes where the connection between the files is visible, which is what was asked for, and where a failed entry has somewhere to be reported. It costs a flattened tree in the model and the uniform-height promise; it does not cost a second row anatomy, a second progress model, or a new view class.

What would change my mind: if a paste of 150 with groups open measures badly once setUniformItemSizes is off. That is a number nobody has, and it is the first thing T-137 should get.
